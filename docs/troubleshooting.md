# 出问题了看这里（dsh-fish 排查手册）

README 只留最常见的三条。这一份收的是那些「一次踩过、以后大概率不会再碰」的坑——不是每次都需要的，但真撞上了能省一晚上。

先确认一件事：**插件装没装进去**。插件自己看不见自己没被加载，所以下面这条脚本要先跑：

```
node tools/check-install.mjs                 # 扫所有 profile
node tools/check-install.mjs --profile desktop
```

零依赖，插件没加载也能跑，会说出是「正常 / 装的是旧副本 / 副本空的或装了一半」，后两种直接给修法。npm 装的话脚本在 `node_modules/@ssamurias/dsh-fish/tools/check-install.mjs`。

---

## 升级了却没变化？先看设置页顶上那张卡（0.8.0）

profile 里写 `"dsh-fish": "file:D:/DSH/plugins-src/dsh-fish"` 时，pnpm 会往 `node_modules\dsh-fish` 落一份**独立副本**，而 DSH 加载的就是副本。只把新版本覆盖到源目录、然后重启——跑起来的还是旧代码，界面没有报错，日志也不会多一行（新代码压根没执行）。

0.8.0 起启动时会比一次：profile 里那条 `file:` 指向的目录版本 vs 正在跑的 `VERSION`。对不上就

- 设置 → **数据** 页靠下的位置出现一张「升级没有真正装进去」的卡（在「导入」卡下面、最底下的重置按钮上面），写清两条修法：关掉 DSH 后 `pnpm install --force`，或者直接删掉 `node_modules\dsh-fish` 再启动；
- 启动日志里留一行 warn，`/state.upgrade` 也带着 `{stale, older, running, source, sourcePath}`。

只有 `link:` 安装、读不到源目录、`package.json` 坏了这几种情况会静默跳过，不影响启动。
**还有一种它查不到的情况：副本是空的。** 如果 pnpm 装到一半失败，`node_modules\dsh-fish` 可能是个空目录（或只有零星几个文件）——这时插件根本没被执行，那张卡也不会出现（卡是插件自己画的）。判断方法很简单：看 `node_modules/dsh-fish\package.json` 在不在、版本号对不对：

```
node -p "require('C:/Users/你/.dsh/profiles/desktop/node_modules/dsh-fish/package.json').version"
```

路径换成你自己的 profile。读不到就是空的：重装一遍（`pnpm install --force`）再启动；**装的时候不要只看命令回显——要看退出码。**

空副本让插件「连自己都没跑起来」，所以「插件自检」这条路在安装失败面前天生看不见；0.8.1 把 `userQuestions` 从 `inject` 里摘掉，就是不想再有第二条同样看不见的静默消失。

## 两个工作区、两个家（0.6.7）

一个工作区只该有一个家。如果同一个 DSH 里两个工作区都装了大肥鱼、又都落到同一个目录（最常见的原因：只搬了**插件文件夹**、没配 `root`，或 `cordis.patch.yml` 里那条 `id` 在升级后对不上），0.6.7 起会**自己认出来**：

- 加载时在数据目录里写 `instance.json`（谁占着、什么时候心跳、进程号、机器名），每 15 秒续一次；45 秒没续、或同一台机器上那个进程已经没了，就当作上一任崩了，新的立刻接管（重启不用等）。
- 认领（读声明、判断、写声明）整段在 `<root>/.instance.lock` 里做，声明用原子写，写完隔 200 毫秒再读一次确认：两个实例同时启动，只有一个当上房主，另一个当场就是只读，不用等到第一次心跳。
- **后进来的那个不写**：`growth_commit` / `her_leave` / `bili_speak` 会直接回一句「这个家被另一个实例占着」，并说明怎么分开；身份文件也不落盘。已经写进去的旧事件不动。
- 每条事件现在带 `sessionId`（谁的哪条会话写的）；工具调用前还会核对**调用者是不是她的那条会话**（按会话 id 认，见下面「他开在她屋子里的会话」一节），不是就拒绝并说明——「谁在写」写进事件里，事后能查。

要真的分成两个家，别复制插件目录，只改配置：在 profile 的 `cordis.patch.yml` 里给这个插件加一条 `root`（`dsh-fish` 的 loader 条目 `id` 要对得上），两个工作区各指一个目录，重启 DSH。升级插件包**不会动** `cordis.patch.yml`（插件只写自己数据目录里的文件），但升级后值得回来看一眼那条 `id` 还在不在。

## 他开在她屋子里的会话（1.0.8）

**症状**：开着大肥鱼时，新建的会话里每个工具调用都回「这件事我做不了」，可工具名单里明明有 `read`、`write`；同一条日志里反复出现「挡住了一次不该有的调用：run_code」。关掉插件就恢复。老会话正常。

**原因**：1.0.7 及以前，插件判断「这条会话是不是她」只看会话的工作目录是不是 `~/.dsh-fish/home`。她的屋子在 DSH 里是一个普通工作区，谁把新建会话落在那个分组下（或客户端把当前选中的工作区传成了它），那条会话的 cwd 就正好等于她的家，于是被当成她——工具面按她的名单收窄，身份段也照挂。它不是「误操作」，是这个判据把文件夹当成了人。

**1.0.8 起**：认人改成按**会话 id**——`home.json` 里记的那条、换房前后的几条、`channels.json` 里每间群房的会话。cwd 只在宿主没给出会话 id 时才拿来做兜底；用户自己在她屋子里开的会话，id 不在台账里，就按普通人对待（全量工具、不挂身份）。建会话那一瞬 id 还没返回，插件用一个只在 `await sc.create(...)` 期间有效的窗口认领它，返回后立刻把 id 记进台账。

**还在旧版本时**：新建会话前，别在大肥鱼的「家」这个工作区分组里点新建——换到别的工作区再开。升级到 1.0.8 后不需要再避开。

## 会话被归档了，为什么不再自动重开（0.6.8）

以前「把她的会话归档」等于「下次启动重开一间」——判活只看工作区的会话清单、又把归档的排掉，归档之后就成了「这个家没有会话」，于是每启动一次多一间。0.6.8 起语义变了：

- 归档 = **收起来**。`home.json` 里记 `status: 'archived'`（含 `archivedAt`），启动时不再自动新建。设置 → 大肥鱼 →「数据」页会出现一张「会话被收起来了」的卡片，点**「重新搭一間」**才会重开（对应 `POST /dsh-fish/home/rebuild`，要带 `confirm: 'rebuild'`）。插件自己的「重置一局」（`/reset`）不受影响，它本来就是要一局新的。
- **同一间房不再并发建两条。** 启动链路和「她要说话」链路都会找会话，现在按 root 单飞（同一个 promise），另外 `home.json` 的 `createdAt` 在 10 分钟内时，即使宿主索引还没列出那条会话也按「可复用」算。
- **换家留痕。** root 改了（`cordis.patch.yml` 里的 `root`）之后，新家从零开始，旧家原封不动留在旧路径——这正是「一夜之间多了个分身」的来源。现在数据目录之外记一份 `~/.dsh-fish-homes.json`（可用 `DSH_FISH_HOMES` 覆盖），root 变了会写一条 `meta` 事件「家换了：A → B。这不是搬家……」，进日志、进 `/state.homes`，设置页数据页顶部也会并排给出两条路径。
- **归档的是那一条，不是整个家。** 以前 `home.json` 只认一条会话，它一归档，插件就说「这个家的会话被收起来了」——哪怕同一个工作区里还有另一条好好开着。现在两条归档判定（`home.json` 的 `status:'archived'` 与宿主的 `archivedSessionIds`）在拒绝之前都先看同屋：还有没归档的会话就认那一条（取 `ws.sessionIds` 里最近的一条），把 `home.json` 改指过去、清掉归档标记，并记一行日志。一条都不剩才说「被收起来了」，也不会因此硬造一条新的。

**换家 ≠ 搬家**：想把她的东西带过去，用「数据 → 迁移工作区」（写 `~/.dsh-fish-location.json` 指针），不要改 `root`。

## 两个实例同时开同一个家（0.8.0）

0.6.8 的单飞锁只在**一个进程内**有效。真把 DSH 开两遍、两边都落同一个 `root` 时，第二个进程照样会走到「建会话」那一步（房客日志里成对的 `home.json.*.tmp` 就是这么来的），于是每开一次多一条会话。0.8.0 补了两处：

- **占用中的家只读**：`instance.json` 显示这个家已被别的实例占着时，启动**什么都不建**（连空工作区也不建），只把 `home.json` 里那条会话报上去，也不叫醒她。设置 → 数据页会出现「这个家在别处也开着」的卡片；关掉另一个实例后，下次启动自动接管。
- **跨进程一把锁**：`ensureTalkSession` 从读 `home.json` 到写回整段在 `<root>/.talk-session.lock` 里跑（`wx` 独占创建、mtime 超过 30 秒算陈旧锁）。等 8 秒还拿不到就不硬建：读一眼 `home.json`，有会话就复用，没有就明确失败，下次再来。

想真正并存，还是那句话：在 `cordis.patch.yml` 给每个条目配**不同的 `root`**，不要让两个实例住同一个家。

## 适配哪些 DSH 版本（0.8.1）

`package.json` 里写了两处，跟市场上的插件用同一套写法：

```json
"engines": { "dsh": ">=0.2.0-rc.1 <0.3.0-0" },
"dsh": {
  "compatibility": {
    "dsh": ">=0.2.0-rc.1 <0.3.0-0",
    "dshReleases": { "0.2.1-rc.2": "compatible", "0.2.1-rc.3": "compatible", "...": "unknown" },
    "profiles": ["desktop", "web", "headless"]
  }
}
```

- `engines.dsh` 是宿主安装/检查时真读的那一条；不满足会作为 `engines.dsh` 报出来。
- `dsh.compatibility.dshReleases` 是逐版本的态度：只在**真跑过**的版本上写 `compatible`，其余写 `unknown`——写 `unknown` 不是「不支持」，是「没测过」。
- 当前写 `compatible` 的是 `0.2.1-rc.2`、`0.2.1-rc.3`（房客与开发机在 0.8.x 上跑过的两个），具体清单以 `package.json` 为准。

运行时还会自己对一次账（`lib/hostver.js`）：从插件所在位置向上找宿主的 `package.json`，读到版本就比范围。

- 在范围里：什么也不说。
- 比自己要求的下限还旧、或超出上限：`logger.warn` 一行，设置页「数据」页多一张卡说明**只提醒、不拦人**——插件照常跑。
- 读不到（桌面版把宿主装进 `app.asar`，从插件位置找不到）：记 `unknown`，不把「读不到」当成「不兼容」，否则每个桌面用户都会看到一张假警告。

**为什么下限是 0.2.0-rc.1 而不是更低**：插件用到的宿主接口（`tools.register/view/restrict`、`sessionController.create/prompt/rename/resolveAgent`、`workspaceRegistry`/`archiveSession`/`setTitle`）在 0.1.x 的包里其实已经有了（查过 `dsh-tools@0.1.0-rc.8`、`dsh-api-session-controller@0.1.2-alpha.2`、`dsh-workspace@0.1.0-rc.8`），但**没有在那些宿主上真跑过**。声明的意义是承诺测过的范围，不是猜一个更大的数。

**这一条管不到的事**：`inject` 里的四个服务（`sessionController`、`tools`、`webServer`、`connection`）仍然是硬依赖——缺任何一个，插件在 import 阶段就被跳过、连日志都不写。这类情况只能从外面查：`node tools/check-install.mjs`。

## 她只想了想，一个字没回（1.0.2）

**现象**：你发一句，侧栏里那一轮很快结束，她一句正文都没有，也没有报错。展开看，那一轮只有一段思考（`reasoning`），没有正文（`text`）块。

**这不是插件把话弄丢了。** 插件对模型输出只读——收 `text` 块当她说出口的话（`lib/turns.js` 的 `assistantText()`），删不了、也补不出。真机抓到的那次（2026-11-14 外部报告）是：模型想到「我该写一句了」就结束了这一步，宿主把「只有思考、没有正文」的这次回复当成正常结束，`turn/end` 照常发下来。同一台机器上五轮里大约出一轮，不稳定复现，跟关不关插件无关。

**怎么确认**：看插件日志。1.0.2 起遇到这种轮次会留一行

```
turns · 这一轮只有思考没有正文（1 条 assistant/message，输出 136 token），她的话没记
```

- 有这一行、`输出` 明显不是 0 ⇒ 模型走了、但没写正文，就是上面这个现象。
- 没有这一行、`turns` 也没涨 ⇒ 不是她屋里那一轮（比如你在别的会话里说话），或者这一轮根本没跑起来。
- 另外，如果你一开口时日志里出现「上一轮叫醒留下的处境被撤掉」，说明那次是「她自己醒的那一轮」的处境串了过来——这个老毛病 2026-11-06 已经修过，真再出现就把这两行一起发出来。

**怎么办**：

1. 点「继续」让她把这一轮说完——宿主 0.2.2-rc.2 起有这个按钮，插件会把这次说的话补进**同一轮**（`amendLastExchange`），不会多算一轮。
2. 或者直接再问一句。插件不「自动补叫一次」：硬叫只会让她凑一句本不该说的话，还会把轮次计数和试吃的口味弄歪。

**这一版做了什么**：只补留痕（上面那行日志），行为一点没动——轮次照结、`talk-recent.json` 照记（她那一轮的话是空的）。往上游修（让宿主别把「只有 reasoning 的 completion」当正常结束）要靠 DSH 那边；这条日志就是为了让下一个报告能直接指到模型/宿主，而不是再花一轮排查插件。

## 她一句话写完，末尾又替对方说了两句，还被记成她的话（1.0.8）

**现象**：她的回复末尾多出两段很短的对白，先替对方说「我得出门了」，再替自己应一声「好，那你先忙，回来再接着聊」。那不是你在说话，也不是插件的回执——模型在同一个 `text` 块里连续吐出来的，`finish` 还是正常的 `stop`。上一版只认行首的 `user:` / `assistant:` 标记，这两段只有空行分段，于是原样落进 `events.jsonl` 的 `utterance`。

**这不是上下文泄漏**：那一轮 `inputTokens` 只有几百，你也没说过这两句；是采样层的续写漂移，复现不了。真机量过：172 个会话、14261 条 `assistant/message`，这种形态只出现 1 次。上下文很长（十几万 cache 读）、你的消息结尾正好是一句对白（`世界：有完没完？`）、以及收尾指令把「回话」和「记一笔」塞在同一句里，三个条件同时在场。

**这一版做了两件事**：① 收尾提示改成「只写你自己说的话——不要替对方写台词……说完就停」，「想留下一句」拆成另一个动作，不再和回话并列；② 记录层多一道窄清洗：末尾两段各自只有一行、都不长，前段有「我」和一个离场词（出门 / 睡了 / 先忙…），后段以「好 / 嗯 / 行」开头、提到你、又约了「回来 / 接着 / 明天」，且前面还有真正文——全满足才从「要走」那段整段切掉，命中留一行

```
turns · 正文末尾像两个人的告别对白，记她的话时切掉了 37 字
```

**故意不做的事**：不按「末尾一段很短、又以好/嗯 开头」这种泛判据清洗。报告人自己在 14261 条上量过，那种筛子命中 14 条只有 1 条是真的，其余全是正常收尾（「那就这样，去睡。」）——会在她真说的话上误伤。所以宁可漏判，也不改写她的话。

**你会看到什么**：侧栏正文里那两句仍然在（界面层不清洗，切错会把真正文删给你看），但 `events.jsonl`、`talk-recent`、下一轮提示词里不再有它。旧记录不会自动改——已经写进去的那一条留在原地，是你和她的历史。



## 她写完真话，又「往下写」了一轮：编出时间头，再把整份提示词默写出来（1.0.8）

**现象**：一条回复一共四千多字。前面是正常的一句话，接着是一段看起来像宿主注入的东西——

```
Time sampled while preparing turn 51, step 1: 2026-11-21T23:29:09+08:00[Asia/Shanghai]
Browser time zone for this call: unavailable. Ask the user to clarify.
Elapsed since the preceding model-visible message: 25m 20s.
```

——再往后就是 `## 你是谁` / `## 现在` / `## 这些天` 一路默写到结尾，差不多四千三百字。这些不是宿主塞进来的：那次会话的 28 条 `system/message` 都是干净的，整段在模型自己的 `stream` 里（2639 片、13700 毫秒、同一个 `assistant/message`，正常 `finish: stop`）。她写的时间也是编的——生成窗口在 23:27:41 就结束了，那个会话根本没有 turn 51。

**为什么会落库**：前两道判据都按设计放行。没有行首 `user:` / `assistant:` 标记（第一道不认），也不是「一个人的告别 + 另一个人的应答」（第二道不认）。整段于是被当成她这一轮说的话，按 2000 字一条切成 `utterance`，同时进了 `talk-recent`——换个会话时还会以「你说：…」搬过去，下一轮读到又可能再写一次。

**这一版做了什么**：`lib/transcript.js` 加第三个判据 `stripPromptEcho()`，只认**行首结构**，不认措辞。上面三行里任何一行出现在行首（允许前置空格），就从那一行起整段切掉；句子中间提到这几个词不算（`宿主注入的那行叫 Time sampled while preparing turn，我照着写就行` 一个字符都不动，有回归用例）。为什么不按措辞匹配：`unavailable. Ask the user to clarify.` 这句宿主真用过，按原文匹配两头都会错。

另外留了一个软信号：正文里整行等于身份文档小节标题的个数 ≥2 时，只写一行日志 `turns · 正文里出现了 N 个身份小节标题，留意`，**不切**——她引用自己设定时也会中，靠它量频率，不靠它动手。

**你会看到什么**：切掉的时候日志里有一行

```
turns · 正文里带回了宿主的时间头，记她的话时从那儿切掉了 4401 字
```

侧栏正文里那一整段仍然在（界面层不清洗，切错会把真正文删给你看），但 `events.jsonl`、`talk-recent`、下一轮提示词里不再有它。已经写进去的旧 `utterance` 不会自动改——那是你和她的历史，插件只追加、不改写。旧版 `talk-recent.json.corrupt.*` 里也见过同类时间头，同样的处理。

**为什么不再收紧一点**：把「正文里出现两个 `## ` 标题」也当成判据会误伤她自己的日记式长回复；这类漂移本来量就很小（真机量到 1 次）。先把结构最硬、误伤为零的那一条钉住，其余只留日志。

## `growth_commit` 少了 `type`，回执却说「未知事件类型：」（1.0.8）

**现象**：她调 `growth_commit` 时参数里没带 `type`，回执是「没记下：未知事件类型：（允许：seed/utterance/…）」，日志里只剩一行

```
[warn] 事件被校验拒收： type=? source=tool 未知事件类型：
```

调用方看到「未知事件类型」只会以为这个类型不被支持，不会想到自己是漏了必填字段，重发时照旧不带——几句话就这么丢了；日志里也看不出「到底收到了哪些键」。

**根因**：`lib/tool.js` 的 `defineTool` 在 npm 安装这条路上是个恒等函数（为什么绕开宿主，见那个文件头），而 DSH 的参数校验只长在宿主 `defineTool` 的 execute 包装里。于是工具定义里写的 `required: ["type","text"]` **从来没有执行过**，缺字段的调用一路走到 `lib/schema.js` 的 `validateEvent`，才以「未知事件类型」收场。会话记录里 `tool/call.arguments` 的原文就没有 `type`，所以也不是宿主吃键。

**这一版做了什么**：① `lib/capture.js` 的 execute 在任何读盘之前先拦一道，缺 `type` 就返回「这次没收到 type（收到的键：confidence / text / topic），所以没写。重发时把 type 写上：utterance / revise / …」——只摆收到的键名，不回显她记了什么；② `lib/store.js` 那条 warn 补了 `keys=…`（空对象写「（空对象）」，不是对象就写它的类型），以后别的字段漏了也能一眼看出来。

**已知 / 有意，这一版没做**：那层 `required` 对**其余工具**依然不生效（`bili_speak`、`ask_owner`、`her_dream`、`bili_look`、`bili_sub`、`her_leave`、`bring_back` 也各写了必填）。原因是改在公共出口（`lib/use.js` 的 `withUse`）会让**所有**工具在缺参数时改成抛错，而 19 个工具现在全都用返回值报失败、且 `output.schema` 形状各不相同——那是一次口径统一，不是补一个洞，得单独一轮做，还得同步改文案和测试。所以这一版只堵最贵的这一个（写事件流的那条），其余靠各工具自己的空值判断兜着：

- `her_leave` 缺 `text` → 「空白的，没留。」
- `ask_owner` 缺 `question` → 「把想问的那句话写出来。」
- `her_dream` 缺 `refs` → 由 `DREAM_NEEDS_REF` 挡

**这些是有意留着的边界，不是漏掉的**：不改也不会写坏数据；代价只是同一故障有几种说法，而且写盘类工具缺字段时不会走到 `appendEvent`，`keys=` 那行也就不会留。**什么时候再收口**：再出现一次「缺参数静默写坏/写空」、或加工具/加字段变频繁、或外部再报同类。收口时也不必一步做到公共出口——照 `growth_commit` 的写法给 5 个写盘类工具（`her_leave`、`her_dream`、`bring_back`、`ask_owner`、`bili_speak`）各加一道入口判断就够了；读盘类（`bili_look`、`bili_sub`）不用管。
